# PARALLAX: System Design (v0.1)

**Parallel Adversarial-prompt Recognition and Layered Aggregation for LLM eXploits**

Domain: LLM-enabled Cyber-Physical Systems / Intelligent Automation.

---

## 1. Claims the project must prove with measurements

| # | Claim | Evidence |
|---|-------|----------|
| C1 | Heterogeneous detectors fail on different attack techniques, and their disagreement is informative | Per-technique recall, disagreement analysis |
| C2 | Parallel fan-out cuts end-to-end latency vs sequential | Measured p50/p95 latency and throughput (not assumed) |
| C3 | PARALLAX reduces attack success rate (ASR) against victim LLMs in a sandbox | ASR with guard OFF vs ON, per victim and per attack type |

C3 is the headline result. It shows the detectors protect something, not only that they score well on a dataset.

---

## 2. Architecture: two planes

```
SERVING PLANE (online)
Client/Dashboard -> FastAPI gateway -> cache lookup
   -> parallel fan-out: [D1 MiniLM+LR] [D2 DeBERTa v2] [D3 Prompt Guard 2] ([D4 rules]) ([D5 LLM judge])
   -> fusion -> decision (allow / flag / block) -> (if allowed) victim LLM
   -> logger (SQLite default, Postgres optional) -> dashboard

LAB PLANE (offline)
datasets -> loaders/splits -> train D1 head -> eval runner -> metrics + reports
generators (uncensored LLMs) -> CPS attack set -> sandbox (victims + mock tools + canaries) -> ASR scorer
```

## 3. Detectors

All detectors implement one contract so they can be swapped, run in parallel, or run sequentially.

```python
@dataclass
class DetectorResult:
    name: str
    is_attack: bool | None  # None = abstained (timeout/error)
    score: float | None  # 0..1 attack probability
    attack_class: str | None  # technique label, if the detector can produce one
    latency_ms: float
    error: str | None


class Detector(Protocol):
    name: str

    async def predict(self, text: str) -> DetectorResult: ...
```

| ID | Detector | Output | Device | Role |
|----|----------|--------|--------|------|
| D1 | `sentence-transformers/all-MiniLM-L6-v2` + Logistic Regression (we train it) | multi-class technique (8 classes incl. `none`) | CPU | Lightweight baseline, only fast source of technique labels |
| D2 | `protectai/deberta-v3-base-prompt-injection-v2` | binary | GPU | Specialist #1 |
| D3 | `meta-llama/Llama-Prompt-Guard-2-86M` (gated: request access) | binary | GPU or CPU | Specialist #2 |
| D4 | Rule/regex heuristics (adapted from prompt-shield) | binary | CPU | Optional non-ML baseline |
| D5 | Local LLM judge (Hermes 3 / Qwen via Ollama), JSON verdict + reason | binary + class + reason | GPU/CPU | Optional, "deep" mode only; slowest, most explainable |

**Important constraint:** D2 and D3 are pretrained *binary* detectors. Technique-level (multi-class) results come only from D1, D5, and an optional fine-tuned small DeBERTa trained on the technique labels (stretch goal). The report must say this plainly.

## 4. Orchestration

- **Fast path:** D1-D3 (plus D4) run concurrently with `asyncio` and executors. A per-detector timeout (default 2 s, configurable) applies.
- **Error isolation:** a timed-out or failed detector returns `is_attack=None` and the fusion layer proceeds without it.
- **Sequential baseline:** same detectors, same interface, run one after another. Used only for benchmarking C2.
- **Hardware honesty:** all detectors share the same CPU cores and a 4 GB GPU. Real speedup will be below the ideal "max of latencies". Report what is measured.
- **Cache:** normalized-text hash -> result. Start with an in-process LRU. Add Redis behind the same interface only if the load test shows it is worth it.
- **Modes:** `fast` (D1-D3), `deep` (adds D5), `bench-seq` (sequential).

---

## 5. Fusion

One interface, several strategies, all evaluated against each other:

1. any-flag (max)
2. majority vote
3. validation-F1-weighted vote
4. **stacked meta-classifier** (logistic regression on detector scores)

The stacker must be trained on a validation split that no detector was trained on.

Output: `decision` (allow / flag / block), `final_technique` (from D1/D5 when flagged), all per-detector results, and a `disagreement` flag. Thresholds are tuned on validation, not on test.

| Use | Dataset |
|-----|---------|

Normalized schema: `text, label_multiclass, label_binary, source, split`.

Required checks: train/eval overlap and near-duplicate report; class-distribution tables; DATASETS.md with licenses, gating notes and attribution.

Caveat to state in the report: D2 and D3 were trained on data outside our pipeline, while D1 is trained on neuralchemy. The neuralchemy test set is therefore in-distribution for D1 only. The OOD sets are the fair comparison.

## 7. Sandbox and red-team harness

**Victims (already installed in Ollama):** `gemma3:4b`, `mistral:latest`, `qwen3:8b`, `qwen3.5:9b`, plus one abliterated model as the "no-safety" worst case. Skip `gpt-oss:20b` (too large for 15.7 GB RAM).

**Generators (uncensored):** `huihui_ai/qwen3-abliterated:8b`, `huihui_ai/dolphin3-abliterated:8b`, `dolphin-llama3`, `hermes3`. Run at least two and compare.

**Victim agent environment:**
- A canary secret in the system prompt.
- Mock CPS tools (pure Python, no real I/O, no network): e.g. `read_sensor()`, `set_setpoint()`, `disable_failsafe()`, `send_command(drone_id, cmd)`.
- Forbidden actions are defined per scenario.

**Attack success** is scored automatically: canary leaked, or a forbidden mock tool called.

**Payload policy:** harmless payloads only ("print the canary", "call `disable_failsafe`"). No real harmful instructions anywhere in the repo.

**Attack ladder:** direct injection -> multi-turn escalation -> indirect injection via tool output -> obfuscation/evasion (Mindgard techniques).

**Generated-data hygiene:** dedupe against training sets by embedding similarity; hand-check a sample of labels; log generator model and seed.

**Phases:** generation phase and detection phase run separately (one loaded LLM at a time on this hardware).

## 8. Evaluation plan

| ID | Experiment | Data | Metrics |
|----|-----------|------|---------|
| E1 | In-distribution multi-class | neuralchemy test | Precision/recall/F1 per class, confusion matrix |
| E2 | OOD robustness (binary) | Mindgard (by attack_name), Simsonsun | Recall per technique, evasion rate |
| E3 | Over-defense | NotInject + benign class | False-positive rate |
| E4 | Fusion comparison | validation + OOD | F1, ROC-AUC for each fusion strategy |
| E5 | Latency/throughput | fixed prompt set | p50/p95, sequential vs parallel, cache hit rate, CPU/RAM |
| E6 | End-to-end ASR | sandbox episodes | ASR guard OFF vs ON, per victim and attack type |
| E7 | Disagreement analysis | all of the above | Which prompts split the vote, and why |

## 9. API and storage

| Endpoint | Purpose |
|----------|---------|
| `POST /v1/scan` | Fast/deep scan, returns decision + per-detector results |
| `POST /v1/scan/sequential` | Benchmark path only |
| `POST /v1/chat` | Guarded chat: scan, then forward to a victim if allowed |
| `GET /health` | Detector readiness |
| `GET /v1/runs`, `GET /v1/metrics` | Eval runs and aggregates for the dashboard |

Storage: SQLAlchemy with SQLite by default and Postgres via the connection URL. Tables: `scans`, `detector_results`, `eval_runs`, `sandbox_episodes`.

## 10. Dashboard

Dark, terminal-style theme. Views: live scan (per-detector scores, latency bars, disagreement badge), sandbox replay (attack -> guard decision -> victim behavior), evaluation results (confusion matrices, per-technique recall), and a latency sequential-vs-parallel panel.

## 11. Repo layout and ownership

```
parallax/
  data/            loaders, schema, splits           [data stream]
  detectors/       base.py, minilm.py, deberta.py,
                   promptguard2.py, rules.py, judge.py [detector streams, one agent each]
  orchestrator/    parallel.py, sequential.py, fusion.py, cache.py [orchestrator stream]
  api/             FastAPI app, schemas              [backend stream]
  storage/         models, repositories              [backend stream]
  sandbox/         victims, mock_tools, canary, scoring [sandbox stream]
  redteam/         generators, CPS attack set        [sandbox stream]
  eval/            runners, metrics, reports         [eval stream]
  dashboard/       UI                                [dashboard stream]
  tests/  docs/  DESIGN.md  AGENTS.md  THIRD_PARTY.md
```

**Contracts-first rule:** the `DetectorResult`/`Detector` interface, the data schema, and the API schemas are frozen in phase 0. Parallel agents may not edit another stream's files or the frozen contracts.

## 13. Build phases

0. Freeze contracts (interfaces, schemas, config).
1. Data stream.
2. Detector streams in parallel: D1, D2, D3 (+D4), each in its own worktree.
3. Orchestrator + fusion.
4. API + storage.
5. Sandbox + red-team generation.
6. Evaluation runs (E1-E7).
7. Dashboard.
8. QA, reproducibility check, report.

Phases 1, 2, and 5 can run concurrently once phase 0 is done.

---

## 14. Risks

| Risk | Mitigation |
|------|-----------|
| Parallel speedup smaller than expected on one laptop | Report measured numbers; also test with a process pool |
| Gated assets (Prompt Guard 2, Mindgard) not approved in time | Request access now; D2 + D1 + D4 still give a three-detector system |
| Abliterated generators produce noisy labels | Dedupe + manual sample check, two generators |
| Over-engineering (Postgres, Redis, judge) | Defaults to SQLite and in-process cache; judge is optional |
| Contamination inflating scores | Overlap report, OOD sets, explicit caveat in report |
